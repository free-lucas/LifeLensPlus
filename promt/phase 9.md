## 实现说明（Phase 9 已完成）

> 这一节是实现方对上面需求的落点说明与取舍记录，需求本身没有改动。

### 一、日记（需求 1.1 / 1.2）

| 需求 | 落点 |
| --- | --- |
| 1.1 日历选一天看当天日记 | 「日记」标签页：月历（周一起始，补满整周）+ 每天的状态点（生成中 / 失败 / 已完成按主要分类着色 / 有区块无日记 / 无记录），点格子切换这一天 |
| 1.1 默认打开前一天 | `createDiaryView` 的选中日初值就是 `shiftDayKey(今天, -1)` |
| 1.2 每次打开补生成 | 启动即扫一次；另外每个本地午夜扫一次、区块汇总状态变化时（2s 合并）再扫一次 |
| 1.2 二阶汇总 | 输入是这一天的全部 10 分钟区块 + 上一天已完成的日记；相邻同项目同分类的连续区块先合并成「时段」，再按 12000 字符预算逐段降级 |
| 1.2 六段内容 | `summary` / `mainEvents`（最多三件）/ `highlights` / `todos` / `suggestions` / `tips`，由 JSON Schema 约束结构，第二层校验兜住内容质量 |

补充约定（需求没写、实现里定的）：

- **今天不生成日记**（这一天还没过完），只处理今天之前的日期；
- 一天还没回填完（还有记录没变成区块）时先不生成，避免出现半篇日记；
- 一篇日记 = `diaries` 表的一行，`day` 是业务主键；行与 AI 任务在同一个事务里落库，扫描天然幂等；
- 失败的日记不自动重试，界面上给「重新生成」按钮（手动重生成会取代排队中的旧任务）；
- 一次启动最多补 30 天（`LIFELENS_DIARY_SCAN_LIMIT`），避免首次启动把队列灌爆。

详见《[18-日记生成](../docs/18-日记生成.md)》与《[19-日记界面](../docs/19-日记界面.md)》。

### 二、看板（需求 2.1 / 2.2）

**2.1 周期**：日 / 周 / 月 / 年四个按钮，外加上一期 / 下一期 / 回到今天 / 跳到某一天。
周期边界（周一起始、自然月、自然年）、标题与前后锚点全部由主进程算好，渲染层不做日期数学。

**2.2 图表**（全部手写 SVG，没有引入图表库）：

| 需求里点名的 | 实现 |
| --- | --- |
| 不同类型的时间花费占比（饼图） | 环形图（`donutSlices` / `renderDonut`）：四类各占一段，圆心写总时长，图例带时长与占比 |
| 不同软件出现次数的排名 | 横向排行条（`rankGeometry` / `renderRankChart`）：按出现次数排序，数值列写「N 次」 |
| 不同项目专注时间的统计 | 同上，数值列写时长；条长按最长项目归一化 |

在需求之外额外做进去的多维度可视化（「尽量用上所有数据」）：

- **活动趋势**：按周期分桶（日 = 24 小时、周 / 月 = 每天、年 = 每月），柱子按四个分类堆叠显示时长，
  折线是该桶里的截图记录数（同一张图里对比「时长」与「记录密度」）；
- **时段分布**：一天 24 小时的时长分布（日视图的「活动趋势」本身就是时段分布，不重复画）；
- **关键词**：来自截图分析的关键词，字号代表出现次数；
- **待办线索**：区块汇总里提到的待办，带上最早出现的那一天；
- **统计卡片**：已汇总时长 / 时间段（失败数作注脚）/ 截图记录 / 活跃天数 / 平均每天。

数据口径：时长 = 区块数 × 10 分钟，只算已汇总且有分类的区块；看板是**只读**的，不写库、不触发 AI。

详见《[20-看板与统计](../docs/20-看板与统计.md)》。
