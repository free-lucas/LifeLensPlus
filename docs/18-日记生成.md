# 日记生成（Phase 9）

## 1. 目标与范围

需求：**每次打开应用时，把之前没有生成的日记补上**；每天的日记是对这一天所有 10 分钟区块的**二阶汇总**。

- 输入：这一天的全部 `time_blocks`（Phase 8 的一阶汇总）+ 上一天已完成的日记；
- 输出：六段内容 —— 简短总结 / 主要事项（最多三件）/ 高光 / 待办 / 优化建议 / 温馨提示；
- 一天一行（`diaries` 表），`day` 是业务主键，重复生成同一天只更新那一行。

不做的事：不做周报 / 月报，不做跨天的时间段切分，不做日记的手动编辑与导出，
不引入新的表去存「日记素材」。

## 2. 时间口径

| 概念 | 口径 |
| --- | --- |
| 一天 | 本地自然日 `YYYY-MM-DD`（`src/main/day.js`） |
| 日键来源 | 本地 ISO 字符串的前 10 个字符（`2026-09-15T09:50:00+08:00` → `2026-09-15`），与 `captured_at` / `block_start` 完全同口径 |
| 区间 | `dayBounds(day)` 返回 `[from, to)`：`2026-09-15T00:00:00+08:00` ~ `2026-09-16T00:00:00+08:00` |
| 今天 | **从不生成今天的日记**：这一天还没过完，生成出来的日记必然不完整 |
| 上一天 | 「比目标日期小、且状态是 `COMPLETED` 的最近一条」，中间没有记录的日子自动跳过 |

`parseDayKey` 是严格校验：`2026-02-31`、`不是日期` 都返回 `null`，调用方再决定兜底（IPC 回退今天）。

## 3. 数据层

### 3.1 `diaries` 表（schema v3）

```sql
CREATE TABLE diaries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    day TEXT NOT NULL UNIQUE,      -- 本地日期 YYYY-MM-DD，业务主键
    status TEXT NOT NULL,          -- PENDING / COMPLETED / FAILED
    block_count INTEGER NOT NULL DEFAULT 0,
    summary TEXT,                  -- 简短总结
    main_events_json TEXT,         -- 主要事项（字符串数组）
    highlights_json TEXT,
    todos_json TEXT,
    suggestions_json TEXT,
    tips_json TEXT,
    model TEXT,
    analysis_ms INTEGER,
    error TEXT,
    error_code TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX idx_diaries_status ON diaries(status);
```

「有没有生成过」完全靠**行是否存在**判断，所以缺口扫描天然幂等：同一天不会重复排队，
失败的行也不会被自动重扫（自动重扫会让一篇永久失败的日记变成无限循环）。

### 3.2 写入：行与 Job 同一事务

`DiaryRepository.upsertDiaryWithJob(entry, job)` 在**一个事务**里写 `diaries` 行 + `ai_jobs` 行，
与截图（`insertActivityWithJob`）、区块（`insertBlockWithJob`）完全同构。任意一步失败整体回滚，
不会留下「有日记行、没任务」或反过来的半成功状态。

`ON CONFLICT(day) DO UPDATE` 只重置 `status / block_count / error / error_code / updated_at`，
**正文保留到新结果落库**：重新生成期间界面上仍然看得到上一篇日记，而不是先被清空。

### 3.3 缺口扫描

```sql
SELECT b.day_key AS day, b.n AS block_count
  FROM (SELECT substr(block_start, 1, 10) AS day_key,
               COUNT(*) AS n,
               SUM(CASE WHEN status = 'PENDING' THEN 1 ELSE 0 END) AS pending
          FROM time_blocks
         WHERE block_start < ?          -- 今天 00:00：今天的日记不生成
         GROUP BY day_key) b
  LEFT JOIN diaries d ON d.day = b.day_key
 WHERE d.day IS NULL AND b.pending = 0 AND b.n > 0
 ORDER BY b.day_key ASC
 LIMIT ?
```

三个条件缺一不可：**没有日记行**、**这一天没有区块还卡在汇总中**、**这一天确实有区块**。
一次最多补 `DIARY_DEFAULT_SCAN_LIMIT = 30` 天（硬上限 365），避免首次启动把队列一次性灌爆。

### 3.4 日历标记

`listDayMarks(fromDay, toDay)` 一次返回一段日期里每一天的：日记状态、区块数、还在汇总的区块数、
时长最长的分类与它的区块数。三条查询（`diaries` 一段、`time_blocks` 按天分组、按天 × 分类分组）
在 JS 里按天合并，界面因此不需要为了画一个月的日历发 30 次请求。

### 3.5 读模型

| 方法 | 用途 |
| --- | --- |
| `getByDay(day)` | 某一天的日记（详情页） |
| `findPreviousDiary(day)` | 生成时的上下文：比它早的最近一条 `COMPLETED` |
| `countByStatus()` | 「正在生成 N 篇」提示与快照 |
| `updateDiary(day, patch)` | 只更新 patch 里出现的字段（与区块 / 活动的回填语义一致） |

## 4. AI 输出

### 4.1 Schema

`DIARY_SCHEMA` 交给 Ollama 的 `format` 参数，六个字段全部 required、`additionalProperties: false`：

| 字段 | 约束 |
| --- | --- |
| `summary` | 40 ~ 400 字 |
| `mainEvents` | 1 ~ 3 条，每条 ≤ 80 字 |
| `highlights` | ≤ 5 条，每条 ≤ 120 字 |
| `todos` | ≤ 10 条，每条 ≤ 200 字 |
| `suggestions` | ≤ 5 条，每条 ≤ 200 字 |
| `tips` | ≤ 3 条，每条 ≤ 150 字 |

第二层校验（`normalizeDiaryResult`）在 Provider 返回后跑：`summary` 少于 40 字判
`INVALID_RESULT`（可重试），`mainEvents` 至少 1 条；数组元素 trim / 去空 / 去重 / 超长截断，
超出条数按顺序截断而不是判失败。

### 4.2 提示词与上下文压缩

一天的区块最多 144 个，逐条塞进提示词会远超上下文窗口。两步处理：

1. **合并时段**（`buildDiarySegments`）：时间连续、分类与项目都相同的相邻区块合并成一段；
2. **按字符预算降级**（`buildContextLines`，预算 `MAX_CONTEXT_CHARS = 12000`）：
   完整行（含最多 2 条最长的描述、每条截断到 160 字）→ 精简行（只留时间段 / 分类 / 项目 / 时长 / 软件）
   → 放不下就丢弃并**计数**，最后如实写一句「还有 N 段时间没有在这里列出」。

提示词结构（**只讲怎么汇总，不描述 JSON 格式**）：

```text
你是生活记录助手。下面是一个自然日里每 10 分钟的活动汇总，请把它们二次汇总成这一天的日记。
日期：2026年9月15日 周二

【这一天的时长分布】工作 3 小时 10 分（19 段）、学习 40 分钟（4 段）

【上一天（2026-09-14）的日记】
<上一天 summary 截断到 200 字 + 主要事项>

【这一天的记录】共 12 段，按时间从早到晚：
09:00–09:40 | 工作 | 写《2026 年中报告》 | 40 分钟 | 软件 Word、Chrome
    描述：…
（这一天还有 2 个时间段汇总失败，没有包含在上面）

要求：
1. summary 用 2~4 句话概括…  2. mainEvents 最多三件…  3. highlights…
4. todos…  5. suggestions…  6. tips…
只写记录里能看到的内容，不要编造；也不要输出 JSON 结构以外的任何文字。
```

### 4.3 Provider

`OllamaDiaryProvider.analyze(job)`：

- 上下文**在执行时才读**（`loadContext`）：这一天的区块可能还在汇总队列里；
- `think: false` —— 混合思考模型开着思考会把 `num_predict` 全烧掉，正文一个字都写不出来；
- `temperature: 0.4`（日记是叙述性文字，不需要像分类那样保守）、`num_predict: 2048`；
- `num_ctx` 与区块汇总共用 `config.numCtx`（同一个 Ollama 实例，上下文必须一致）；
- 返回 `blockCount`（这一天参与汇总的区块数，写进 `diaries.block_count`）与
  `logLine = describeDiary(diary)`（只有条目数量，**不带正文**）。

## 5. 调度

`DiaryGenerator` 与 `TimeBlockSummarizer` 在区块链路上的角色对称：扫描缺口 → 入队 → 回填 → 快照。

| 触发点 | 说明 |
| --- | --- |
| 应用启动 | `start()` 立刻扫一次，补上应用没运行的那些天 |
| 本地午夜 | 到下一个本地午夜 + 5s 再扫（让这一天最后几个区块先汇总完） |
| 区块状态变化 | 每次区块汇总完成 / 失败都通知一次，2s 内合并成一次扫描 |

**回填优先级**：区块回填是严格按时间从后往前的，所以「这一天还有记录没变成区块」等价于
「这一天不早于最早的那个缺口日期」。`backfillCeiling()` 取最早缺口所在的日期，凡是不早于它的候选日
一律 `deferred`——否则日记只看得见这一天的一部分。今天的缺口不算天花板（今天本来就不生成日记）。

重入保护：`scan()` 用 `scanning` 标志挡住并发调用，第二次直接返回 `{ busy: true }`。

## 6. 队列接入

- Job 类型 `DIARY_GENERATION`，幂等键是 `payload.day`（`jobPayloadKey` 依次取
  `screenshotId ?? blockStart ?? day`）；
- 扫描入队用 `priority = LOW`（先让截图分析与区块汇总跑完）；
- **手动「重新生成」用 `force: true`**：先去重表里把同一天还在排队（`PENDING` / `RETRYING`）
  的旧任务取消掉，再建新任务。否则用户点了按钮会被去重悄悄吞掉（正在推理的 `PROCESSING`
  按状态机不可取消，此时仍然去重）；
- 结果回填 `handleResult` 写正文 + `COMPLETED`；永久失败 `handleFailure` 写 `FAILED` + `error_code`，
  行保留，界面给「重新生成」入口。

## 7. 崩溃恢复

- 日记行与 Job 在同一个事务里落库，崩溃只会丢掉「两个都没写」的那一次，不会出现半成功；
- 队列启动时把 `PROCESSING` / `RETRYING` 恢复成 `PENDING`，日记任务和截图任务走同一套恢复；
- `PENDING` 的日记行不会因为重启而丢失（行还在），扫描只补「没有行」的日子，
  已有 `PENDING` 行的日子由队列里的任务继续跑完。

## 10. 留给后续 Phase 的问题

- 一天里的区块数量变化（例如补录了新的区块）不会自动重算已经 `COMPLETED` 的日记，
  只能手动「重新生成」；
- `FAILED` 的日记不会自动重试（避免无限循环），只能手动重新生成；
- 上下文压缩在极长的一天（144 段全部有描述）下仍会丢段，只是会把丢掉的段数如实写进提示词；
- 日记的「上一天」上下文只取一天，跨天的长任务（例如连着三天的报告）看不到更早的线索。
