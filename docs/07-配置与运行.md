# 配置与运行

## 1. 环境变量

`src/main/config.js` 只从环境变量读配置（同名前缀 `LIFELENS_`），没有配置文件。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `LIFELENS_DIR` | `<系统图片目录>/LifeLensPlus` | 数据根目录：数据库 + 截图 |
| `LIFELENS_INTERVAL_MS` | `20000` | 截屏间隔（毫秒） |
| `LIFELENS_MODEL` | `qwen3-vl:8b` | Ollama 模型 |
| `LIFELENS_OLLAMA_HOST` | `http://127.0.0.1:11434` | Ollama 地址 |
| `LIFELENS_ANALYZE_TIMEOUT_MS` | `120000` | 单张截图分析超时（毫秒）；生产形态实测只要 1~4 秒，一般不需要调大 |
| `LIFELENS_AUTOSTART` | `1` | 设为 `0` 则启动后不自动开始记录 |
| `LIFELENS_AI_CONCURRENCY` | `1` | AI Worker 并发数 |
| `LIFELENS_AI_MAX_RETRIES` | `3` | 最大重试次数 |
| `LIFELENS_AI_HEALTH_POLL_MS` | `15000` | Ollama 离线时的健康探测间隔 |
| `LIFELENS_AI_MAX_TERMINAL_JOBS` | `500` | `ai_jobs` 里保留的终态任务上限 |
| `LIFELENS_SUMMARY_MODEL` | 同 `LIFELENS_MODEL` | 10 分钟区块汇总用的 Ollama 模型 |
| `LIFELENS_SUMMARY_TIMEOUT_MS` | `300000` | 单次区块汇总超时（毫秒）；生成约 1000 字比单张截图分析慢得多 |
| `LIFELENS_SUMMARY_SCAN_LIMIT` | `144` | 一次扫描最多补多少个待汇总区块（144 个 = 24 小时） |
| `LIFELENS_DIARY_MODEL` | 同 `LIFELENS_SUMMARY_MODEL` | 日记用的 Ollama 模型 |
| `LIFELENS_DIARY_TIMEOUT_MS` | `300000` | 单篇日记超时（毫秒）；一天最多 144 个区块，比单个区块汇总慢 |
| `LIFELENS_DIARY_SCAN_LIMIT` | `30` | 一次扫描最多补多少天没生成的日记 |
| `LIFELENS_NUM_CTX` | `16384` | Ollama 上下文长度（输入与输出共享同一个窗口）；`0` 表示不传，用 Ollama 自己的默认值 4096 |
| `LIFELENS_EMBEDDING_MODEL` | `bge-m3` | 本地 embedding 模型（与视觉 / 汇总模型相互独立） |
| `LIFELENS_EMBEDDING_DIMENSION` | `0` | 向量维度；`0` 表示第一次调用后自动探测（bge-m3 是 1024） |
| `LIFELENS_EMBEDDING_TIMEOUT_MS` | `60000` | 单次 `/api/embed` 请求超时 |
| `LIFELENS_EMBEDDING_BATCH_SIZE` | `32` | 一次嵌入多少条 |
| `LIFELENS_EMBEDDING_SCAN_INTERVAL_MS` | `60000` | 待嵌入记录的扫描间隔 |
| `LIFELENS_EMBEDDING_MAX_BATCHES` | `10` | 一轮扫描最多连续处理多少批 |

Phase 6 移除了 `LIFELENS_JOBS_FILE`：任务队列固定存在 `<LIFELENS_DIR>/lifelens.db`，没有单独配置项。

embedding 相关配置改动后重启本应用即可；换 embedding 模型时 `LIFELENS_EMBEDDING_DIMENSION`
必须同步改（或留 `0` 让 Provider 自己探测），否则和已有向量表的维度对不上。

`LIFELENS_NUM_CTX` 同时作用于截图分析、区块汇总与日记，几边必须是同一个值，否则 Ollama 会在不同
上下文配置之间来回重载模型。它随每次请求下发，所以改这个值**不用重启 Ollama**，重启本应用即可；
需要重启 Ollama 的只有 `ollama serve` 自己的 `OLLAMA_CONTEXT_LENGTH`（本项目不使用它）。
为什么定 16384、不显式抬高会怎样，见《[15-时间区块汇总](15-时间区块汇总.md)》第 5.1 节。

`LIFELENS_ANALYZE_TIMEOUT_MS` 同时是两处守卫：`chatWithOllama()` 里的 HTTP 中止，以及 Worker
的兜底竞速（`main.js` 把同一个值交给视觉 Provider）。超时按 4 次尝试计入最坏占用
（`4 × 超时 + 退避 22s`），所以**调大它不会让正常请求变快，只会拉长卡死请求独占 Worker 的时间** ——
实测生产形态单张只要 1~4 秒，默认 120 秒已有约 30 倍余量。分析见
《[37-截图分析性能](37-截图分析性能.md)》。
注意它和其他几个超时一样走 `num()`，**`0` 是合法值**（会被原样下发），而超时为 0 意味着每个请求
立即中止、任务全部失败 —— 要「等于没有超时」请给一个很大的值，不要写 0。

## 2. 目录结构

```text
<LIFELENS_DIR>/
├── lifelens.db                 活动记录 + AI 任务队列（SQLite）
├── lifelens.db-wal             WAL（运行期间存在；正常退出后 checkpoint 回主库）
├── lifelens.db-shm             共享内存索引
└── <YYYY-MM>/
    └── images/
        └── <YYYY-MM-DD_HH-mm-ss-SSS>.png
```

- 时间格式：`formatLocalIso()` 输出带时区偏移的 ISO-8601（秒级），例如 `2026-09-13T21:26:23+08:00`。
- 截图文件名：`imageStamp()` 输出 `2026-09-13_21-26-23-446`，去掉扩展名就是 `screenshot_id`。
- 旧版本生成的 `*.json` 文件可能还留在目录里，程序不会读取它们。
- `lifelens.db` 里除了 `activities` / `ai_jobs`，还有 Phase 8 的 `time_blocks`（10 分钟区块汇总）
  与 Phase 9 的 `diaries`（一天的日记）。

Phase 10 的向量索引在**另一处**（Electron 的用户数据目录，不在 `<LIFELENS_DIR>` 下）：

```text
<userData>/lancedb/
├── activity_vectors.lance
├── block_vectors.lance
└── diary_vectors.lance
```

它是可随时重建的语义索引，删掉不会丢任何原始数据（把三张表的 `embedding_status` 重置为
`PENDING` 后服务会重新嵌入）。Windows 上 `<userData>` 默认是
`%APPDATA%\<应用名>`（应用名取自 `package.json` 的 `name`，即 `lifelens-plus`），
用 `--user-data-dir` 启动时以该目录为准。

## 3. 运行

```bash
npm install
npm start
```

- `npm install` 装 Electron 与 `@lancedb/lancedb`；SQLite 使用 Node 内置模块。
  LanceDB 是 napi 预编译包，不需要 `electron-rebuild`（Node 22 与 Electron 44 实测都能直接加载）。
- 首次启动会自动开始记录；窗口右上角可以暂停 AI、查看队列状态与事件日志。
- 单实例锁：重复启动会立即退出并聚焦已有窗口（两个实例同时写同一个库是不允许的）。

## 5. 常见问题

| 现象 | 原因 / 处理 |
| --- | --- |
| 启动时弹「本地数据库初始化失败」 | 数据目录不可写、数据库文件损坏或版本高于当前程序；检查目录权限 / 备份后删除 `lifelens.db` 重建 |
| 控制台出现 `ExperimentalWarning: SQLite is an experimental feature` | 预期现象；`node:sqlite` 仍是实验 API，不要为消除警告引入 native 依赖 |
| 界面记录列表是空的，但磁盘上有旧 `*.json` | Phase 6 不迁移旧 JSON，属预期；旧记录不会出现在界面与统计中 |
| 任务一直停在 `PENDING` | Ollama 没启动或模型没拉取；启动 Ollama 后 Worker 会自动继续 |
| 退出后目录里还有 `lifelens.db-wal` | 非正常退出（被强杀）时的残留，下次启动 SQLite 会自动恢复，不影响一致性 |
| 头部的「汇总中」标记一直在 | 有待汇总的时间段或正在扫描；首次用旧数据库时会补齐历史缺口，144 个区块一轮，慢慢收敛 |
| 动态页显示「汇总中…」很久不变成内容 | Ollama 没启动、模型没拉取，或 `LIFELENS_SUMMARY_MODEL` 指的模型不存在；汇总走独立的健康检查 |
| 某个时间段显示「汇总失败」 | 该区块永久失败（重试用尽 / 结果不合法），不会自动重试，也没有手动重新汇总的入口；重排方法见表格下方 |
| 区块汇总的描述像是丢了前半段记录 | 提示词装不进上下文时 Ollama 会**静默**砍掉前半段、只保留末尾约 2050 token；调大 `LIFELENS_NUM_CTX`（默认 16384 实测够用）后重启本应用；不需要动 Ollama |
| 某一天的日记一直显示「正在生成…」 | 这一天还有区块卡在汇总中，或 Ollama / 模型不可用；日记任务排在区块汇总之后（`priority = LOW`），区块收敛后会自动继续 |
| 某一天的日记显示「生成失败」 | 该日记永久失败（重试用尽 / 结果不合法），不会自动重试；在日记页点「重新生成」即可重排，不需要动数据库 |
| 昨天的日记没有生成 | 昨天还有记录没变成 10 分钟区块（回填没补完）时会先等区块补齐；也可能是应用在这天之后一直没启动过，启动补扫一次最多补 30 天（`LIFELENS_DIARY_SCAN_LIMIT`） |
| 事件日志里反复出现 `EMBEDDING_OFFLINE` | embedding 模型没拉取（`ollama pull bge-m3`）或 Ollama 没启动；记录会留在 `PENDING`，模型恢复后自动补齐，不影响截图与分析 |
| 记录已分析完，但向量库里没有它 | 扫描间隔是 60 秒（`LIFELENS_EMBEDDING_SCAN_INTERVAL_MS`），稍等即可；仍是 `PENDING` 就看事件日志里的 `EMBEDDING_OFFLINE` / `EMBEDDING_ERROR` |
| 事件日志里出现 `EMBEDDING_ERROR ... 退回 PENDING` | 单批嵌入或写向量库失败（模型掉线 / 磁盘问题），下一轮自动重试；持续出现时先确认 Ollama 与磁盘 |
| 升级后老记录全都没有向量 | 这是预期的：升级只把 `embedding_status` 初始化为 `PENDING`，之后由后台扫描逐批补齐 |

### 5.1 重新汇总失败的区块

`time_blocks` 的一行就是一段 10 分钟区块的「处理凭据」：**行存在 = 处理过**，所以缺口扫描只找
「有记录但没有行」的时间段。失败的区块行会被保留（状态 `FAILED`），因此光重启不会重试。

想重排就把这些行删掉，下次启动时会当作从没汇总过重新排队：

```bash
# 先退出 LifeLensPlus（同一个库不允许两个实例同时写）
node -e "const{DatabaseSync}=require('node:sqlite');const d=new DatabaseSync(process.argv[1]);d.prepare('DELETE FROM time_blocks WHERE status = ?').run('FAILED');d.close()" "C:\Users\<你>\Pictures\LifeLensPlus\lifelens.db"
```

一次最多补 144 个区块（`LIFELENS_SUMMARY_SCAN_LIMIT`），超过就等下一轮。

### 5.2 重建向量索引

LanceDB 只是语义索引，坏了、删了、换 embedding 模型之后都可以整库重建，SQLite 的原始数据一行不动：

1. 退出 LifeLensPlus（向量库在写的时候不能删）；
2. 删掉 `<userData>/lancedb/` 整个目录；
3. 把三张表的状态重置为 `PENDING`（下面几行存成临时脚本，路径换成自己的 `lifelens.db` 再 `node` 跑）；
4. 重新启动应用：启动补偿 + 首轮扫描会把存量逐批嵌入。一轮最多 10 批 × 32 条
   （`LIFELENS_EMBEDDING_MAX_BATCHES` × `LIFELENS_EMBEDDING_BATCH_SIZE`），数据多时多跑几轮即可。

```js
const { DatabaseSync } = require('node:sqlite');
const db = new DatabaseSync('C:/Users/<你>/Pictures/LifeLensPlus/lifelens.db');
for (const table of ['activities', 'time_blocks', 'diaries']) {
  db.prepare(`UPDATE ${table} SET embedding_status = 'PENDING', embedding_model = NULL, embedding_version = NULL`).run();
}
db.close();
```
