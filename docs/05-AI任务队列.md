# AI 任务队列

代码：`src/main/ai/AIJobQueueService.js`（调度）+ `src/main/ai/AIWorker.js`（执行）。
Phase 6 只把持久化介质从 JSON 换成 SQLite，状态机与调度行为完全不变。

## 1. 状态机

```text
PENDING ──> PROCESSING ──> COMPLETED
   │             │
   │             ├──> RETRYING ──> PENDING      （可重试失败 / 超时，退避后重排）
   │             └──> FAILED                    （永久失败 / 重试用尽）
   └──> CANCELLED                               （尚未开始）
FAILED ──> PENDING                              （手动重新分析）
```

非法跳转（例如 `COMPLETED -> PROCESSING`）一律拒绝，由 `canTransition()` 判定。
每次状态变更都会调用 `_persist()`，把内存快照同步到 `ai_jobs`。

## 2. 重试与超时

- 默认最多重试 3 次，退避 2s / 5s / 15s（`retryDelaysMs`），绝不无限重试。
- 单次推理超时默认 120 秒（`analyzeTimeoutMs`），超时按可重试错误处理。
  注意超时与重试会**叠加放大**：最坏情况 `4 × 120s + 退避 22s ≈ 8.4 分钟`独占 Worker，
  期间所有截图只能排队，而重试本身还会再烧一遍 GPU。截图分析曾经常态化撞上这条线，
  根因是模型开着思考，见《[37-截图分析性能](37-截图分析性能.md)》。
- 可重试：连不上 Ollama、请求超时、Ollama 5xx、空结果或结构不合法（`INVALID_RESULT`）。
- 不重试：`MODEL_NOT_FOUND`、`IMAGE_NOT_FOUND`、`IMAGE_INVALID`、`OLLAMA_BAD_REQUEST`、
  `STRUCTURED_OUTPUT_UNSUPPORTED`、`JOB_CANCELLED`。
- Ollama 离线：任务留在 `PENDING`，Worker 按 `healthPollMs`（默认 15s）探测，恢复后自动继续。

## 3. 去重与优先级

- `_dedupe(type, key, force)`：同一个**幂等键**的同类任务只保留一条。键由 `jobPayloadKey(payload)`
  统一给出：截图任务取 `payload.screenshotId`，10 分钟区块汇总（Phase 8）取 `payload.blockStart`。
  正在跑的返回 `DUPLICATE_ACTIVE`；已完成的返回 `ALREADY_COMPLETED`（除非显式 `force` 重新分析）。
- 优先级：`HIGH=10` / `NORMAL=5` / `LOW=1`。实时截图走 `NORMAL`，启动补偿与区块汇总走 `LOW`，
  保证新截图的记录先被分析。
- `enqueue()`、`enqueueWithActivity()`、`enqueueWithBlock()` 共用同一份去重实现，
  区别只在于后两者会把对应记录（Activity / 区块）放进同一个事务一起入库。

## 3.1 多 Provider（Phase 8）

`AIWorker` 的构造参数新增 `providers`：一个「Job 类型 -> Provider」的覆盖表，没配的类型退回默认
`provider`。当前接线是截图分析走视觉 Provider、`TIMEBLOCK_SUMMARY` 走文本 Provider
（`summaryProvider.js`）。由此带来三处调整：

- **兜底超时按 Provider 走**：`_timeoutFor(job)` 读 `provider.timeoutMs`，
  汇总 300s、截图 120s，互不影响。
- **健康检查并发探测所有 Provider**：模型可用性按 Provider 分别记录（`modelAvailability`），
  汇总模型缺失时不会把截图分析一起判失败（反之亦然）。
  `snapshot()` 里的 `modelAvailable` 仍然表示主 Provider（视觉模型）。
- **回填按类型分流**：`onCompleted` / `onFailed` 在 `main.js` 里按 `job.type` 分给
  `TimeBlockSummarizer.handleResult` / `handleFailure` 或 `Recorder` 的对应方法。

区块汇总任务的 payload 是 `{ blockStart, blockEnd }`；它不关联 `activities`，
`ai_jobs.activity_id` 固定为 `NULL`。进度与结果记在 `time_blocks` 表。
扫描编排见《[15-时间区块汇总](15-时间区块汇总.md)》。

## 4. 持久化：快照同步

队列每次把内存里的**完整任务列表**交给 `AIJobRepository.save(jobs)`，在**一个事务**里完成：

```sql
-- 1) 逐条 upsert（状态、重试次数、时间戳、错误、payload 全部覆盖；type/created_at 保持原值）
INSERT INTO ai_jobs (...) VALUES (...) ON CONFLICT(id) DO UPDATE SET ...
-- 2) 删除已经不在列表里的行（终态裁剪因此也发生在这个事务里）
DELETE FROM ai_jobs WHERE id NOT IN (?, ?, ...)
```

好处：

- SQLite 与内存不会出现两份不一致的状态
- 终态任务裁剪（默认上限 500 条）与快照写入是原子的，不会裁剪到一半
- 占位符数量随快照长度变化，按长度缓存 prepared statement

`_persist()` 返回写链 Promise；`flush()` 用于退出前等待最后一次写入完成。

## 5. 启动补偿

`Recorder.recoverPendingAnalyses()`：

1. `activities.listPendingRecords()` 取所有 `analysis_status='PENDING'` 的记录
2. 已有任务（含 `COMPLETED` / `FAILED` / `CANCELLED`）的一律跳过 → `skipped`
3. 没有任务记录的调用 `enqueueAnalysis(record, { priority: LOW })` 补建 → `created`
4. 结果记入 `RECOVERY_SCAN` 事件日志

与截图路径的区别：补偿只建 Job，**不写 Activity、也绝不删除截图**——
记录本来就已经存在（典型来源是「记录写完、任务入队之前」进程被关闭）。

## 6. 与存储层的关系

- 队列只认识 `repository.load()` / `repository.save()` 与 `activities` 两个接口，不写 SQL。
- `AIJobRepository._activityId(job)` 在保存时把 `SCREENSHOT_ANALYSIS` 任务关联到 `activities.id`；
  找不到对应记录时写 `NULL` 并记 `STORAGE_ERROR`（正常事务保证下不会发生）。
- 任务裁剪只影响 `ai_jobs` 表，不会删除 `activities`：截图记录与分析结果长期保留。
