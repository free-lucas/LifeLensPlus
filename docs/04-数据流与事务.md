# 数据流与事务

## 1. 一次截图的完整路径

```text
Recorder.tick()
  1. await this.ready（首次统计加载完成）
  2. capture.capturePrimaryDisplay()          截主屏
  3. capture.frameSignature(image)            缩成 32x18 灰度网格（画面指纹）
  4. capture.isSimilarFrame(sig, last)        相似帧 -> 丢弃，不保存/不记录/不入队
  5. store.saveImage(png, startedAt)          写 <LIFELENS_DIR>/<YYYY-MM>/images/xxx.png
  6. aiQueue.enqueueWithActivity(record)      Activity + Job 单事务落库
  7. 更新内存统计并广播事件
```

第 3、4 步的比较规则见《[38-相似帧过滤](38-相似帧过滤.md)》。

第 6 步失败时（`Recorder.enqueueWithActivity`）：

- 调用 `discardScreenshot(imagePath)` 删除第 4 步刚写入的 PNG，避免产生「有图片、没有记录」的孤儿文件
- 删除失败只记录 `STORAGE_ERROR` 日志，不假装成功
- 异常继续向上抛，由 `tick()` 的 catch 记入 `lastError` 并广播，**截图循环不中断**

## 2. Activity + Job 是同一个事务

`ActivityRepository.insertActivityWithJob(record, job)`：

```js
withTransaction(db, () => {
  const result = insertActivityStatement.run(...activityValues(record, now));
  const activityId = Number(result.lastInsertRowid);
  insertJobStatement.run(...jobValues(job, { activityId, now }));
  return activityId;
});
```

- `BEGIN IMMEDIATE` 直接取写锁，避免「先读后写」升级锁失败
- 任意一步抛错 → `ROLLBACK` → 内存队列也不会多出任务（`this.jobs.push(job)` 在事务成功之后才执行）
- 因此不存在「记录写了、任务没建」的半成功状态，`ai_jobs.activity_id` 也一定指向真实存在的行

`Job` 对象的内存生命周期：
`createJob()` → `insertActivityWithJob()`（落库）→ `this.jobs.push(job)` → 事件日志 `JOB_ENQUEUED` → 唤醒 Worker。

## 3. 分析结果回填

| 结果 | 写入 | 说明 |
| --- | --- | --- |
| 成功 | `analysisStatus=COMPLETED`、`analysis` 六个字段、`model`、`analysisMs`、清空 error | `updateAnalysis()` |
| 永久失败 | `analysisStatus=FAILED`、`error`、`errorCode` | 截图与记录保留，可手动重新分析 |
| 记录已被清理 | 不写入 | 广播一条提示事件，任务不判失败 |

`updateAnalysis(screenshotId, patch)` 只更新 patch 里出现的字段（等价于 JSON 时代的 `Object.assign` 语义），
所以「失败回填」不会把上一次成功的结构化结果抹掉；UPDATE 的列组合按列名缓存 prepared statement。

## 4. 崩溃恢复

| 崩溃时的状态 | 恢复动作 |
| --- | --- |
| `PROCESSING` | `queue.start()` 载入后发现进程已退出 → 置回 `PENDING`、清空 `startedAt`/`error`，记 `JOB_RECOVERED` |
| `RETRYING` | 同上，退避计时器随进程消失，直接回到 `PENDING` 重新排队 |
| `PENDING` | 原样继续 |
| 截图已落盘、Job 从未建立 | 启动补偿扫描 `analysis_status='PENDING'` 的记录，缺任务则补建（`JOB_PRIORITY.LOW`） |

`_recoverStuckJobs()` 是崩溃恢复专用的强制改状态：`PROCESSING -> PENDING` 不在正常状态机里，
只在队列启动时由这一条路径写入，并立即 `_persist()` 落库。

### 4.1 10 分钟区块（Phase 8）

区块走的是**同一个形状**的事务：`TimeBlockRepository.insertBlockWithJob(block, job)` 在一个事务里
写 `time_blocks` 行与 `ai_jobs` 行。由此得到一条关键不变式：

```text
time_blocks 里存在这个 block_start  <=>  这个时间段已经排过队
```

于是缺口扫描（`listMissingBlocks`）不需要额外的状态列，也天然幂等。三种中断位置的行为：

| 崩溃时的位置 | 恢复动作 |
| --- | --- |
| 事务提交之前 | 区块行与任务都不存在 → 缺口扫描重新排队 |
| 事务提交之后、汇总完成之前 | 任务停在 `PROCESSING` → `queue.start()` 恢复为 `PENDING` 继续跑；区块行已存在，扫描**不会**重复排队 |
| 汇总完成之后 | 区块 `COMPLETED`，扫描跳过 |

汇总结果回填（`updateSummary`）与 `updateAnalysis` 语义一致：只更新 patch 里出现的字段。
永久失败写 `FAILED` + `error` / `error_code`，区块与描述都保留。

## 5. 启动顺序（main.js）

```text
1. openDatabase()            mkdir + PRAGMA + migration；失败 -> 弹窗提示并退出
2. new ActivityRepository()
2b. new TimeBlockRepository() （Phase 8）
3. new AIJobQueueService()   （注入 AIJobRepository + ActivityRepository + TimeBlockRepository）
4. new Recorder() / AIWorker() / TimeBlockSummarizer()
5. registerIpc() + createWindow()
6. await aiQueue.start()     载入 ai_jobs，PROCESSING/RETRYING -> PENDING
7. aiWorker.start()
8. recorder.recoverPendingAnalyses()   后台扫描补偿，不阻塞窗口
9. summarizer.start()        立刻补扫历史区块缺口，之后每 10 分钟边界再扫
10. config.autoStart 时 recorder.start()
```

先 `await aiQueue.start()` 再扫描补偿，保证「已经有任务」的记录能被内存队列识别并跳过，
不会重复建任务（见 `test/recovery.test.js` 的重启场景）。
`summarizer.start()` 放在窗口创建之后：首次扫描发生的「汇总中」状态要能广播到界面。

## 6. 退出顺序（before-quit）

```text
recorder.stop()                          停止排期
await recorder.whenIdle()（最多 5s）      等在途这一轮写完记录
summarizer.stop()                        停止区块扫描定时器
aiQueue.stop()                           停止接受新任务，清退避计时器
await aiWorker.stop({ timeoutMs: 8000 }) 等在途分析结束
await aiQueue.flush()                    等最后一次写库完成
closeDatabase(db)                        WAL checkpoint 后关闭连接
app.quit()
```

严格保证 `close()` 之后不会再有 `UPDATE ai_jobs`：Worker 与 Recorder 都已停止、写链也已排空。
来不及完成的任务保持 `PROCESSING`，下次启动恢复为 `PENDING`。

## 7. 数据库故障时的降级行为

- **启动失败**（目录不可写、文件损坏、版本高于程序）：`dialog.showErrorBox` 后退出，
  不在没有主存储的情况下静默运行（那样只会安静地丢数据）。
- **运行中单次写失败**（`enqueueWithActivity` 抛错）：删除刚写的截图、记日志、跳过这一条，
  定时器继续跑下一轮，截图系统不会被一次数据库故障永久拖死。
- **队列持久化失败**：`_persist()` 捕获异常并记 `STORAGE_ERROR`，内存队列继续工作，
  下一次状态变更会再次尝试写入。
