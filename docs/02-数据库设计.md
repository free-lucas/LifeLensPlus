# 数据库设计

数据库文件：`<LIFELENS_DIR>/lifelens.db`，驱动为 Node 内置 `node:sqlite`（`DatabaseSync`）。

## 1. 连接级 PRAGMA

打开连接时按以下顺序设置（`src/main/db/database.js`）：

| PRAGMA | 值 | 原因 |
| --- | --- | --- |
| `foreign_keys` | `ON` | 外键默认关闭，必须每个连接显式打开 |
| `journal_mode` | `WAL` | 崩溃/断电后可恢复到一致状态，读写不互相阻塞 |
| `busy_timeout` | `5000` | 偶发锁竞争时等待而不是立刻抛 SQLITE_BUSY |
| `synchronous` | 默认 `FULL` | 不为性能牺牲 durability；本地单写入者，性能足够 |

打开流程：`mkdir` 数据目录 → 建连接 → 设 PRAGMA → 跑 migration → 失败则先 `close()` 再抛出。

## 2. activities

一张截图一行，`screenshot_id` 是业务主键（截图文件名去掉扩展名）。

```sql
CREATE TABLE activities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    screenshot_id TEXT NOT NULL UNIQUE,
    captured_at TEXT NOT NULL,
    image_path TEXT NOT NULL,
    analysis_status TEXT NOT NULL,
    activity TEXT,
    summary TEXT,
    category TEXT,
    project TEXT,
    keywords_json TEXT,
    confidence REAL CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1)),
    model TEXT,
    analysis_ms INTEGER,
    error TEXT,
    error_code TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

| 列 | 约定 |
| --- | --- |
| `screenshot_id` | 例如 `2026-09-13_21-26-23-446`，与磁盘文件名一一对应，UNIQUE |
| `captured_at` | 沿用 `formatLocalIso()`，形如 `2026-09-13T21:26:23+08:00`（带时区，秒级精度） |
| `image_path` | 当前沿用绝对路径：Worker 靠它读图、Renderer 靠它打开截图 |
| `analysis_status` | 只有三种值：`PENDING` / `COMPLETED` / `FAILED` |
| `keywords_json` | 关键词数组的 JSON 文本（如 `["VS Code","Electron"]`），读取时容错解析 |
| `confidence` | 0~1，DDL 层 CHECK 兜底；应用层校验在 `structuredOutput.js` |
| `created_at` / `updated_at` | 行创建与最后更新时间，同一套带时区 ISO 格式 |

失败时 `error` / `error_code` 记录原因，记录与截图都保留，便于后续重新分析。

## 3. ai_jobs

队列的持久化快照。`id` 是 `createJob()` 生成的业务 ID，`activity_id` 指回 `activities.id`。

```sql
CREATE TABLE ai_jobs (
    id TEXT PRIMARY KEY,
    type TEXT NOT NULL,
    activity_id INTEGER,
    status TEXT NOT NULL,
    priority INTEGER NOT NULL DEFAULT 5,
    retry_count INTEGER NOT NULL DEFAULT 0,
    max_retries INTEGER NOT NULL,
    error_code TEXT,
    error_message TEXT,
    last_error TEXT,
    payload_json TEXT,
    created_at TEXT NOT NULL,
    started_at TEXT,
    completed_at TEXT,
    failed_at TEXT,
    updated_at TEXT NOT NULL,
    FOREIGN KEY (activity_id) REFERENCES activities(id)
);
```

| 列 | 约定 |
| --- | --- |
| `type` | `SCREENSHOT_ANALYSIS`（单张截图）与 `TIMEBLOCK_SUMMARY`（10 分钟区块汇总，Phase 8） |
| `activity_id` | 只有 `SCREENSHOT_ANALYSIS` 会填；找不到对应记录时写 `NULL` 并记 `STORAGE_ERROR`。区块汇总任务固定为 `NULL`（它关联的是 `time_blocks`，由 payload 里的 `blockStart` 承载） |
| `payload_json` | `{ screenshotId, imagePath, capturedAt }` 或 `{ blockStart, blockEnd }`，读取时容错解析。幂等键由 `jobPayloadKey()` 统一给出：`screenshotId ?? blockStart` |
| `error_code` / `error_message` | 由 `job.error` 拆出（`code` / `message`） |
| `last_error` | 最近一次失败原因的文本 |
| 时间列 | `started_at` / `completed_at` / `failed_at` 未发生时为 `NULL` |

刻意**没有** `next_attempt_at`：重试退避是内存里的 `setTimeout`，进程重启后 `RETRYING` 一律恢复为 `PENDING`，
所以不需要持久化「下次尝试时间」，也就不会出现重启后按旧时间点乱跑的问题。

## 4. time_blocks（Phase 8）

一段**已结束的** 10 分钟区块一行，`block_start` 是业务主键
（本地 ISO 字符串，与 `captured_at` 同一格式，字符串比较即时间比较）。

```sql
CREATE TABLE time_blocks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    block_start TEXT NOT NULL UNIQUE,
    block_end TEXT NOT NULL,
    status TEXT NOT NULL,
    activity_count INTEGER NOT NULL DEFAULT 0,
    project TEXT,
    category TEXT,
    description TEXT,
    software_json TEXT,
    todos_json TEXT,
    model TEXT,
    analysis_ms INTEGER,
    error TEXT,
    error_code TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

| 列 | 约定 |
| --- | --- |
| `block_start` | 区块起点的本地 ISO，例如 `2026-09-15T10:00:00+08:00`，UNIQUE（业务主键，`id` 只是自增代理键） |
| `block_end` | 起点 + 10 分钟 |
| `status` | `PENDING`（已入队、还没汇总）/ `COMPLETED` / `FAILED` |
| `activity_count` | 入队时该时段的记录条数，仅作参考（之后可能还有新记录落进来） |
| `project` | 「动作 + 《名称》」的短句，如 `写《2026 年中报告》`；同上一个区块延续时同名 |
| `category` | 中文四选一：`娱乐` / `工作` / `学习` / `社交` |
| `description` | 约 1000 字的活动描述（校验下限 200 字，上限 4000 字） |
| `software_json` / `todos_json` | 字符串数组的 JSON 文本，读取时容错解析（非法 JSON / NULL 都退化成 `[]`） |
| `model` / `analysis_ms` | 本次汇总用的模型与耗时 |
| `error` / `error_code` | 失败原因，记录保留便于后续重新汇总 |
| `created_at` / `updated_at` | 同一套带时区 ISO 格式 |

设计要点：

- **区块行与 `ai_jobs` 行在同一事务里写入**（`insertBlockWithJob`），所以
  「区块行存在」就等于「这个时段已经排过队」。缺口扫描因此不需要额外的状态列，
  也天然幂等（见 [15-时间区块汇总](15-时间区块汇总.md) 第 3.1 节）。
- 汇总结果按字段拆开存，与 `activities` 的做法一致，方便筛选与统计。
- 汇总任务不关联 `activities`，所以 `ai_jobs.activity_id` 对这类任务是 `NULL`。

## 5. diaries（Phase 9）

一天的日记一行，`day` 是业务主键：本地日期 `YYYY-MM-DD`，与 `block_start` / `captured_at`
的前 10 个字符同口径。日记是「这一天所有 10 分钟区块」的二阶汇总，所以正文按六段拆开存。

```sql
CREATE TABLE diaries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    day TEXT NOT NULL UNIQUE,
    status TEXT NOT NULL,              -- PENDING / COMPLETED / FAILED
    block_count INTEGER NOT NULL DEFAULT 0,
    summary TEXT,                      -- 简短总结
    main_events_json TEXT,             -- 主要事项（最多三件）
    highlights_json TEXT,
    todos_json TEXT,
    suggestions_json TEXT,
    tips_json TEXT,
    model TEXT,
    analysis_ms INTEGER,
    error TEXT,
    error_code TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

- 五个 `*_json` 列是字符串数组，读取时容错解析（坏数据返回 `[]`，不影响这一天的其余内容）；
- 「有没有生成过」靠**行是否存在**判断，所以缺口扫描天然幂等：已经生成过的日期不会被重复排队，
  失败的日期也不会被自动重扫（自动重扫会让一篇永久失败的日记变成无限循环）；
- 重新生成同一天走 `ON CONFLICT(day) DO UPDATE`，**只重置状态与错误，正文保留到新结果落库**；
- 行与 AI Job 在同一个事务里写入（`DiaryRepository.upsertDiaryWithJob`），
  不会留下「有日记行、没任务」的半成功状态。

## 6. 索引

按真实查询建，不做投机索引：

```sql
CREATE INDEX idx_activities_captured_at ON activities(captured_at);          -- 最近记录列表
CREATE INDEX idx_activities_analysis_status ON activities(analysis_status);  -- 启动补偿扫描 PENDING
CREATE INDEX idx_ai_jobs_status ON ai_jobs(status);                          -- 队列快照 / 统计
CREATE INDEX idx_ai_jobs_activity_id ON ai_jobs(activity_id);                -- 活动 -> 任务关联
CREATE INDEX idx_time_blocks_status ON time_blocks(status);                  -- 「汇总中」计数
CREATE INDEX idx_diaries_status ON diaries(status);                          -- 「正在生成 N 篇日记」计数
CREATE INDEX idx_activities_embedding_status ON activities(embedding_status);  -- Phase 10 待嵌入扫描
CREATE INDEX idx_time_blocks_embedding_status ON time_blocks(embedding_status);
CREATE INDEX idx_diaries_embedding_status ON diaries(embedding_status);
```

`screenshot_id` 的 `UNIQUE` 约束自带索引，重复插入同一张截图会直接失败（不会产生重复记录）。

`idx_activities_captured_at` 同时服务两条读路径：界面的「最近记录」列表（`ORDER BY captured_at DESC`），
以及 Phase 7.1 的 Timeline 查询（`captured_at >= ? AND captured_at < ?` + 倒序 + `LIMIT/OFFSET`）。
Timeline 没有新增表、列或索引。

`time_blocks` 只建 `status` 一条索引：按 `block_start` 范围查询（动态时间线分页、热力图的
12 小时窗口）都走 `block_start` 的 `UNIQUE` 自带索引，不需要额外索引。
`diaries` 同理：日历与详情都按 `day` 范围 / 等值查询（`UNIQUE` 自带索引），只有「按状态计数」
需要一条索引。

Phase 10 的三条 `embedding_status` 索引服务同一个查询：
`WHERE ... = 'COMPLETED' AND embedding_status = 'PENDING'`（见第 9 节）。

## 7. 行 ↔ 业务对象映射

- `ActivityRepository.toRecord(row)`：数据库行还原成 Phase 5 的 Activity Record
  （`id` / `time` / `imagePath` / `analysisStatus` / `analysis` / `model` / `analysisMs` / `error` / `errorCode`）。
  只要结构化列里有任意一列非空就还原出 `analysis` 对象，否则为 `null`。
- `AIJobRepository.toJob(row)`：还原成与 JSON 时代完全一致的 Job 对象，
  因此 `AIWorker` / `Recorder` 对存储切换零感知。
- `ActivityRepository.queryTimeline(options)`：Timeline 的分页查询（时间范围 / `limit` / `offset`），
  `items` 复用同一套行映射，所以状态、结构化结果与 `keywords` 的处理和 `listRecent` 完全一致
  （详见 [09-Timeline数据层](09-Timeline数据层.md)）。
- `jobRow.js` 统一维护 `ai_jobs` 的列顺序与取值映射，`INSERT_JOB_SQL`（事务内插入）与
  `UPSERT_JOB_SQL`（快照持久化）共用同一份列表，避免两处漂移。
- `TimeBlockRepository.toBlock(row)`：数据库行还原成区块业务对象
  （`id` / `start` / `end` / `status` / `activityCount` / `project` / `category` / `description` /
  `software` / `todos` / `model` / `analysisMs` / `error` / `errorCode`），
  `software_json` / `todos_json` 在这里解析成数组，`start` 与 `id` 同值。
- `DiaryRepository.toDiary(row)`：数据库行还原成日记对象
  （`id` / `day` / `status` / `blockCount` / `summary` / `mainEvents` / `highlights` / `todos` /
  `suggestions` / `tips` / `model` / `analysisMs` / `error` / `errorCode`），
  五个 `*_json` 列在这里解析成数组，`id` 与 `day` 同值。

## 8. 写入约定（踩过的坑）

- `prepared statement.run()` **不接受 `undefined` 与布尔值**：所有可空字段统一收敛成 `null`
  （`jobValues()` / `activityValues()` 负责）。
- `PRAGMA user_version = ?` 不支持参数绑定，只能用字符串拼接；拼进去的值只来自代码里的整数常量。
- Windows 上数据库连接未关闭时删不掉所在目录（`EBUSY`），测试的 `cleanup` 必须先关连接再删临时目录。

## 9. embedding 状态列（Phase 10）

三张表各加三列，结构完全一致（migration v4）：

```sql
ALTER TABLE <表> ADD COLUMN embedding_status  TEXT NOT NULL DEFAULT 'PENDING';
ALTER TABLE <表> ADD COLUMN embedding_model   TEXT;
ALTER TABLE <表> ADD COLUMN embedding_version TEXT;
CREATE INDEX idx_<表>_embedding_status ON <表>(embedding_status);
```

| 列 | 约定 |
| --- | --- |
| `embedding_status` | `PENDING`（待嵌入）/ `PROCESSING`（本批处理中）/ `COMPLETED` / `FAILED`（永久失败，只能手动重置） |
| `embedding_model` | 生成这条向量的模型名（如 `bge-m3`），未嵌入时为 `NULL` |
| `embedding_version` | 嵌入版本（如 `v1`），换模型 / 换文本构造时可以靠它识别旧向量 |

- 默认值是 `PENDING`，所以**升级后存量记录自动进入待嵌入队列**，不需要单独的数据迁移；
- 状态列只由 `EmbeddingSourceRepository` 读写（SQL 不出仓库层）；
- `embedding_status` 与 `analysis_status` / `status` 是两套独立状态：只有「分析已完成」的记录才会被扫到；
- 向量本身不在 SQLite 里，LanceDB 的三张表与字段结构见
  《[22-记忆索引-embedding与LanceDB](22-记忆索引-embedding与LanceDB.md)》第 2 节。
