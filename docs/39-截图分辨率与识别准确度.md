# 截图分辨率与识别准确度

代码：`src/main/capture.js`（`ANALYSIS_MAX_SIDE`、`prepareForAnalysis`）。
本篇回答：**为什么本地模型常常把截图「理解错」，以及这和分辨率、提示词各是什么关系。**

## 1. 结论

模型（`qwen3-vl:8b`）本身没问题。错在两个地方叠加：

| 原因 | 作用 | 证据 |
| --- | --- | --- |
| **送进模型的分辨率太低**（主因） | 界面文字糊掉 → 读不出文件名 / 函数名 → 模型不承认「看不清」，而是**编一个像样的名字** | 同一张图，压到 1600/2400 编出不存在的文件名，按原尺寸送入读对 |
| **提示词里的「合格」示例**（放大器） | 示例写的正是本项目的 `analyzer.js` / `chatWithOllama`，与真实屏幕高度相似；模型一旦读不出真名，就直接把示例抄成答案 | 1600/2400 下输出与示例逐字相同；删掉示例后该行为消失 |

本次只改分辨率（`ANALYSIS_MAX_SIDE`：1600 → 3840）。提示词示例仍未改，见第 8 节。

## 2. 现象：模型把提示词示例当答案抄

`structuredOutput.js` 的提示词里有这样一对示例：

```text
不合格：编写代码、浏览网页、看视频、处理文档
合格：在 VS Code 中改 analyzer.js 的 chatWithOllama、在 Chrome 里查 Tailwind grid 文档
```

「合格」示例里的 `analyzer.js` 与 `chatWithOllama` **就是这个项目自己的文件和函数**，
而用户真实屏幕上经常正是这个项目的 VS Code 与文档。于是模型读不清具体文件名时，
输出的就是这句示例本身，且 `confidence` 给到 0.9~1.0，看起来完全可信。

库里 4095 条记录的 activity 分布，同一机制在更早一版提示词上留下过更夸张的痕迹：

| activity | 条数 |
| --- | --- |
| 浏览网页 | 1784 |
| 编写代码 | 1535 |
| 观看视频 | 375 |

前三条合计 3694 条 = **90.2%**，而这三个短语正是提示词里明列的「不合格」示例。
按天看这个塌缩的边界很干净：

| 日期 | 总数 | 通用短语 | 占比 |
| --- | --- | --- | --- |
| 2026-09-25 | 1400 | 1388 | 99.1% |
| 2026-09-26 | 1763 | 1688 | 95.8% |
| 2026-09-27 | 6 | 0 | 0% |
| 2026-10-01 | 5 | 0 | 0% |

09-27 起归零，说明上一轮提示词修正确实治好了「只写动作大类」。但同一台机器上
（`temperature: 0.2`，见 `analyzer.js`）示例仍然会被抄，只是换成了新的那句。

含 `chatWithOllama` 的记录按天：09-26 共 12 条、09-27 共 3 条、10-01 共 4 条 —— 修好之后仍在。

## 3. 实测：同一张图，只改送入分辨率

截图 `2026-10-01_14-05-10-591.png`（3440x1440）。先按原分辨率裁图确认真实画面：
VS Code 的活动标签是 `promt/codex.lanced.gitnexus用法.md`，正文是
`--dangerously-bypass-approvals-and-sandbox`、`approval_policy = "never"` 这些命令行；
Chrome 里是 ChatGPT 的提示词讨论页。

| 送入尺寸 | 提示词 | activity 输出 | 判定 |
| --- | --- | --- | --- |
| 1600x670 | 生产 | 在 Chrome 中查看 LifeLinePlus 页面、在 VS Code 中编辑 analyzer.js 的 chatWithOllama | ✗ 抄示例 |
| 2400x1005 | 生产 | 在 VS Code 中改 analyzer.js 的 chatWithOllama | ✗ 抄示例 |
| 3440x1440 | 生产 | 在 VS Code 中编辑 codex.lanced.gitgenuix.md 文件 | ✓ 读对 |
| 3440x1440 | 生产 | 在 VS Code 中修改 phase5.md 和 phase6.md 的安全策略配置参数 | ✓ 读对 |
| 1600x670 | 去掉示例 | 参考 LifeLinePlus 文档并编辑代码文件（summary 里编出 `colored-glowing-glowing.md`） | ✗ 不抄了，改成另一个编造的名字 |
| 2400x1005 | 去掉示例 | 在 VS Code 中编辑 LifeLensPlus 项目代码 | ✗ 不编名字，但过于笼统 |

两个变量各自的作用被分得很干净：

- **删掉示例**只能消除「抄示例」，不能消除「编名字」——1600 下换成了别的假文件名。
- **提高分辨率**才能让模型**读到真名**：原尺寸下文件名、sandbox 参数、标签页都对上了，
  示例的痕迹消失。

`codex.lanced.gitgenuix.md` 里的 `gitgenuix` 是 `gitnexus` 的轻微误读：字号很小时仍会有
个别字母出错，但「是哪个文件」这个量级的信息已经拿到了（对比 1600 下凭空编造）。

顺带说明这不是模型的锅也不是人眼的锅：把这张图压到 1600x670 后，人工目视同样会把
活动标签读成别的文件。

## 4. 改动

```js
// src/main/capture.js
const ANALYSIS_MAX_SIDE = 3840;   // 原为 1600
```

语义从「为了省 token 主动缩小」改成「只做超大屏兜底」：**4K 及以下的屏幕一律原样送入**。
`prepareForAnalysis()` 本身没有改，缩图规则不变，只是对绝大多数屏幕不再触发。

## 5. 代价：图像 token

同一张图（`2026-10-01_14-05-10-591.png`）实测 `prompt_eval_count`：

| 送入尺寸 | prompt token |
| --- | --- |
| 1600x670 | 1415 |
| 3440x1440 | 4383 |

约 3.1 倍，多出约 3000 token。默认 `num_ctx: 16384`（`config.js`）完全装得下，
即使 4K 全屏（3840x2160）也留有充足余量。

墙钟时间没有可辨变化，落在同一噪声区间内：

| 送入尺寸 | 墙钟 |
| --- | --- |
| 1600x670 | 16.7 s |
| 2400x1005 | 12.3 ~ 21.5 s |
| 3440x1440 | 15.4 ~ 20.0 s |

原因见《[37-截图分析性能](37-截图分析性能.md)》：图像编码是固定成本，且与提示词长度无关，
瓶颈从来是生成侧。

### 与 num_ctx 的耦合（必须知道）

旧注释担心的是「3440x1440 约 4100+ token，超过 Ollama 默认的 4096 上下文而报 400」。
这条风险在提高分辨率后**没有消失**，只是被默认配置挡住了：`LIFELENS_NUM_CTX` 一旦调成 0
（交给 Ollama 决定，默认 4096），4K 截图就会因为装不下直接报 400。

## 7. 已知局限：截图里出现应用自身的历史卡片

第三张验证图 `2026-10-01_14-17-06-648.png` 仍然输出了「在 VS Code 中改 analyzer.js 的
chatWithOllama」。放大原图确认：**这张截图里 LifeLensPlus 自己的窗口正显示着历史分析卡片**，
卡片文字就是「…chatWithOllama 函数，涉及 sandbox 和 workspace 相关配置。同时在 Chrome」
（即 14:05 那条记录）。模型读到的字没错，它把这些**过去**的记录当成了**此刻**的活动。

这不是分辨率问题，提高分辨率也治不好：画面里确实写着这些字。
它是「录制自己的界面」时必然出现的自指干扰，目前没有处理。

## 8. 遗留问题（本次未处理）

- **提示词「合格」示例仍在**（`structuredOutput.js`）：示例用的就是本项目的
  `analyzer.js` / `chatWithOllama`，与用户真实屏幕撞车概率高。去掉示例能消除「抄」，
  但在低分辨率下模型会改成编造别的名字，所以它只能作为分辨率的补充，不能替代。
- **`think: false` 并非总能压住思考**：实验中有一版请求返回的 `content` 以 `<think>` 开头，
  耗时 178 s 后以「AI 返回的不是合法 JSON」（`INVALID_RESULT`）失败。该错误码是可重试的，
  而生产 `analyzeTimeoutMs` 是 120 s，这类请求会先撞超时再重试，可能重现
  《[37-截图分析性能](37-截图分析性能.md)》里的阻塞形态。
- **5K / 6K 屏幕仍会被压到 3840**：属于有意的兜底，未实测这些分辨率下的识别效果。
