# 时间区块汇总（Phase 8）

## 1. 目标与范围

每 10 分钟把这一时段的所有截图分析结果**汇总成一条结构化活动说明**，并参考上一个 10 分钟的汇总
保持项目名称连续。应用启动时补扫历史缺口，界面上用「汇总中」标记排队情况。

这一段回答的是「用户这 10 分钟在做什么」，与单张截图回答的「这一帧在做什么」是两个层次：

| | 单张截图分析 | 10 分钟区块汇总 |
| --- | --- | --- |
| 输入 | 一张 PNG | 该时段的 Activity 记录（含未分析完的）+ 上一区块汇总 |
| 模型入口 | `/api/chat` + 图片 | `/api/chat` + 纯文本 |
| 结构化输出 | `activity` / `category` / `project` / `keywords` / `confidence` | `project` / `category` / `description` / `software` / `todos` |
| 分类口径 | 英文枚举（`coding` / `browsing` …） | 中文四类：娱乐 / 工作 / 学习 / 社交 |
| 落地位置 | `activities` 表 | `time_blocks` 表 |
| Job 类型 | `SCREENSHOT_ANALYSIS` | `TIMEBLOCK_SUMMARY` |

两套分类刻意不共用：截图分类描述「这一帧在做什么」，区块分类描述「这 10 分钟属于哪类活动」，
强行映射只会把信息压扁。

本阶段没有改动 Recorder 的截图链路，也没有改 `activities` / `ai_jobs` 的任何列。

## 2. 时间口径

代码：`src/main/summary/timeBlock.js`。

- `BLOCK_MINUTES = 10`，区块起点按**本地时间**向下对齐到 10 的整数倍，秒与毫秒归零。
- 区块业务键 `blockKeyOf(date)` = 区块起点的 `formatLocalIso()` 字符串，例如
  `2026-09-15T10:00:00+08:00`。**与 `activities.captured_at` 同一格式**，所以
  「一个记录属于哪个区块」在 SQL 里就是字符串比较，不需要在应用层扫全表。
- `createBlock(value, { activityCount, status })` 生成区块业务对象，`id` 与 `start` 同值。
- 区块状态只有 `PENDING` / `COMPLETED` / `FAILED` 三种。

SQL 侧的对齐表达式（`TimeBlockRepository.blockStartExpression()`）与 JS 逐字符一致：

```sql
substr(captured_at, 1, 14)
  || printf('%02d:00', (CAST(substr(captured_at, 15, 2) AS INTEGER) / 10) * 10)
  || substr(captured_at, 20)
-- 2026-09-15T10:07:23+08:00 -> 2026-09-15T10:00:00+08:00
```

时区偏移从第 20 个字符起原样保留，因此跨时区写法（`+08:00` / `Z`）不会被改写。

## 3. 数据层

表结构见《[02-数据库设计](02-数据库设计.md)》第 4 节。读写入口是
`src/main/db/repositories/TimeBlockRepository.js`，SQL 只出现在这里。

| 方法 | 用途 |
| --- | --- |
| `insertBlockWithJob(block, job)` | 区块行 + AI Job 在**同一个事务**里落库（与截图的 `enqueueWithActivity` 同构） |
| `getByStart(blockStart)` | 按业务键读一个区块 |
| `findPreviousSummary(blockStart)` | 取 `< blockStart` 且 `status='COMPLETED'` 的最近一条，作为上一时段上下文 |
| `countByStatus()` | `{ total, completed, failed, pending }`，驱动「汇总中」标记 |
| `listMissingBlocks({ before, limit })` | **缺口扫描**：有记录、没有区块行、且已结束的区块 |
| `updateSummary(blockStart, patch)` | 汇总结果回填（只更新 patch 里出现的字段） |
| `queryBlocks(options)` | 动态时间线的分页查询（时间 / 项目 / 软件筛选 + limit / offset） |
| `listBlocksBetween(from, to, { limit })` | 热力图：一段连续时间内的全部区块，按时间正序 |
| `listFacets()` | 筛选下拉选项：`{ projects, software }` |

### 3.1 缺口扫描

```sql
SELECT b.block_start, b.n
  FROM (SELECT <对齐表达式> AS block_start, COUNT(*) AS n
          FROM activities WHERE captured_at < ? GROUP BY block_start) b
  LEFT JOIN time_blocks t ON t.block_start = b.block_start
 WHERE t.block_start IS NULL
 ORDER BY b.block_start ASC LIMIT ?
```

「有没有处理过」不靠额外状态列判断，而是靠**区块行的存在性**：行与任务是同一事务写的，
行存在就说明任务一定建过。因此扫描天然幂等，重复跑不会给同一个区块排两次队。

`before` 传当前区块的起点，所以只处理**已经结束**的区块，正在进行的 10 分钟不汇总。

### 3.2 筛选与分页

`queryBlocks` 的 `from` 是闭区间、`to` 是开区间（`[from, to)`），与 Timeline 一致。
软件筛选用 `json_each` 精确匹配单个名字：

```sql
EXISTS (SELECT 1 FROM json_each(time_blocks.software_json) WHERE value = ?)
```

不用 `LIKE`，避免「Code」把「Visual Studio Code」误判成命中。
页大小 `LIMIT` 默认 20、上限 100；热力图一次读一段连续时间，走 `listBlocksBetween`，上限 288（48 小时）。

## 4. AI 输出

代码：`src/main/ai/summaryOutput.js`。

### 4.1 Schema

JSON 结构交给 Ollama 的 `format` 参数约束，不在提示词里描述格式：

```js
{
  project:     string,                       // 「玩《荒野大镖客》」「写《2026 年中报告》」
  category:    enum['娱乐','工作','学习','社交'],
  description: string,                       // 1000 字左右
  software:    string[] (maxItems 20),
  todos:       string[] (maxItems 10),
}
// required: 全部五个字段；additionalProperties: false
```

### 4.2 第二层校验

Schema 只约束语法，业务合法性在 `normalizeSummaryResult()` 里再判一次：

| 字段 | 规则 | 不合法时 |
| --- | --- | --- |
| `project` | 非空字符串，≤ 60 字 | `INVALID_RESULT`（可重试） |
| `category` | 必须命中四个枚举值 | `INVALID_RESULT`（可重试） |
| `description` | **< 200 字判失败**；> 4000 字截断 | `INVALID_RESULT`（可重试） |
| `software` | 数组、去空去重、≤ 20 条、单条 ≤ 60 字 | 类型错判失败；超出部分截断 |
| `todos` | 同上，≤ 10 条、单条 ≤ 200 字 | 同上 |

描述太短说明模型没按要求写，重试有意义；描述太长只截断不判失败——重试也未必更短，
而内容本身是有价值的。

### 4.3 提示词

`buildSummaryPrompt({ blockStart, blockEnd, records, previous })` 负责「怎么汇总」：

- 顶部给出时间段（`10:00–10:10`）。
- 有上一个区块时插入【上一个 10 分钟的汇总】（项目 / 分类 / 软件 / 描述，描述截断到 300 字供参考），
  并要求「如果这段时间是上一个 10 分钟的延续，**必须沿用完全相同的项目名称**」。
- 【本时段的记录】按时间从早到晚逐行列出，每行压缩成
  `10:03:12 编写代码 | 在 VS Code 里编辑 recorder.js | 分类 coding | 项目 Life Lens | 关键词 Electron`。
  **还没分析出结果的记录也如实带上**（写成「（还没有分析结果）」），不凭空跳过。
- 五条要求分别对应五个输出字段，并明确「只写记录里能看到的内容，不要编造」。

## 5. Provider

代码：`src/main/ai/summaryProvider.js`。

`OllamaSummaryProvider` 只认识「上下文 → 提示词 → 结构化结果」，不碰 SQL：

- 构造参数 `{ ollamaHost, model, timeoutMs, loadContext, healthTimeoutMs, numCtx }`。
- `loadContext({ blockStart, blockEnd })` 由 `main.js` 注入，执行时**现读**数据库：
  `records` 来自 `activities.listSummaryContext()`，`previous` 来自 `timeBlocks.findPreviousSummary()`。
  之所以不在入队时读，是因为区块刚结束时最后几张截图可能还在分析队列里。
- 请求走 `analyzer.js` 抽出的 `chatWithOllama()`（与视觉分析共用同一层 HTTP 调用与错误分类），
  参数为 `temperature: 0.3`、`num_predict: 2048`、`num_ctx`。汇总是叙述性文字，比分类任务可以
  放松一点；不显式给 token 上限会把 1000 字描述截断，不显式给上下文长度会被静默截断（见 5.1）。
- **必须传 `think: false`**。`qwen3-vl` 是混合思考模型，开着思考时它会把 `num_predict`
  全部烧在思考上，`message.content` 始终为空，汇总只会得到
  「汇总失败：AI 返回了空结果 / INVALID_RESULT」。实测（Ollama 0.34 + `qwen3-vl:8b`）：

  | `think` | `num_predict` | done_reason | eval_count | `message.thinking` | `message.content` |
  | --- | --- | --- | --- | --- | --- |
  | 默认（开着） | 2048 | `length` | 2048 | 3946 字思考文本 | **空** |
  | 默认（开着） | 8192 | `length` | 3687 | 6610 字，还在思考 | **空** |
  | `false` | 2048 / 4096 | `stop` | 213~284 | **完整 JSON** | **空** |

  关掉思考后一次汇总只要 200~300 token、13~23 秒。
- 关掉思考的副作用是 **Ollama 0.34 会把整个约束输出放进 `message.thinking`，`content` 反而是空的**。
  `chatWithOllama()` 因此统一按「`content` 非空就用 `content`，否则退到 `thinking`」取值，
  两种落点都能拿到结果，两条链路都不需要特殊解析。
- **视觉分析同样必须显式传 `think: false`**，理由与汇总完全一样。早期这里写过
  「截图任务简单、开着思考也能在预算内写完」，已被实测推翻：同一张图开思考生成
  1250 个 token（13.0 s），关掉只生成 72 个（0.74 s），最坏单张 12132 个 token / 145.7 s。
  详见《[37-截图分析性能](37-截图分析性能.md)》。
- `this.timeoutMs` 同时被 Worker 读取（见下），汇总的时间预算比单张截图长得多。

`model` 默认复用视觉模型（`LIFELENS_SUMMARY_MODEL` > `LIFELENS_MODEL` > 默认值），
本地只拉了一个模型时不需要额外配置。

### 5.1 上下文长度与截断

`chatWithOllama()` 只在 `numCtx > 0` 时把 `num_ctx` 写进请求体的 `options`，值来自
`LIFELENS_NUM_CTX`。`main.js` 把同一个 `config.numCtx` 同时交给视觉分析与汇总——
**两边必须是同一个值**，否则 Ollama 会在两个上下文配置之间反复重载模型。

不传 `num_ctx` 时 Ollama 0.34 用默认窗口 **4096**。实测（同一段满员区块的提示词，
`think: false` + `num_predict: 2048`，每次请求前先 `ollama stop` 清掉前缀缓存）：

| 提示词 token | `num_ctx` | `prompt_eval_count` | 结果 |
| --- | --- | --- | --- |
| 1889 | 不传（4096） | 1889 | 完整 |
| 3201 | 不传（4096） | 3201 | 完整 |
| 3578 | 不传（4096） | 3578 | 完整，但只剩约 500 token 给输出 |
| 3956 | 不传（4096） | 3956 | 完整，输出被压到 140 token |
| 6008 | 不传（4096） | **2050** | **被截断**：只保留末尾约 2050 token |
| 6008 | 16384 | 6008 | 完整 |

- 规律：**装得下就完整处理；装不下不是按比例丢一点，而是直接砍掉一半、且只保留末尾。**
  本项目的提示词把「要求」放在末尾，所以截断后指令还在，丢的是前面那些记录——
  汇总会凭空少掉半个区块，而且不报错、不重试。
- 20 秒间隔下一个区块正好 30 条记录，实测提示词 1889~3201 token（取决于记录文字长度与是否带上
  一区块摘要），已经贴着 4096 的天花板；记录再长一点就会一步跌到 2050。
- 显存（`ollama ps`）：4096 → 5.8 GB，8192 → 6.5 GB，16384 → 7.8 GB，32768 → 10 GB。
  KV cache 约 0.147 MB/token 线性增长，模型标称的 262144 上下文仅 KV cache 就要约 38 GB，
  16 GB 显卡放不下，所以取「实测够用 + 留余量」的 16384。
- `num_ctx` 是**按请求**下发的参数，改它**不需要重启 `ollama serve`**：Ollama 会自己卸载并按新
  窗口重载（实测 8192 → 16384 重载 9.4s，之后常驻，第二次请求 82ms）。

## 6. 调度

代码：`src/main/summary/TimeBlockSummarizer.js`。与 Recorder 在截图链路上的角色对称。

```text
start() ─┬─> scan()           立刻补扫历史缺口（应用没运行时留下的时间段）
         └─> scheduleNext()   到下一个 10 分钟边界 + 2s 再扫
                                      │
             listMissingBlocks ───────┘
                      │
        enqueueWithBlock(block, { priority: LOW })
                      │
        Worker 完成后按 Job 类型分流到 handleResult / handleFailure
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `DEFAULT_SCAN_DELAY_MS` | 2000 | 区块结束后等 2s 再汇总，让最后几张截图的记录先落库 |
| `DEFAULT_SCAN_LIMIT` | 144 | 一次扫描最多补 144 个区块（24 小时），避免首次启动把队列一次性灌爆 |

- `scan()` 有并发保护（`scanning` 标志），重复调用直接返回 `{ busy: true }`。
- `nextDelayMs()` = 到下一个区块边界的毫秒数 + 扫描延迟；`now` 正好落在边界上时等下一个完整区块
  （刚结束的那个由本次扫描处理）。
- 定时器 `unref()`，不拖住进程退出。
- `snapshot()` 返回 `{ running, scanning, blockMinutes, stats }`，是「汇总中」标记与 IPC 的数据源。
- 扫描失败会记 `STORAGE_ERROR` 事件并返回 `{ error }`，不会让定时循环停掉。

## 7. 队列接入

- 新 Job 类型 `AIJobType.TIMEBLOCK_SUMMARY`，payload 为 `{ blockStart, blockEnd }`。
- 幂等键由 `jobPayloadKey(payload)` 统一给出：截图任务取 `screenshotId`，区块任务取 `blockStart`。
  `enqueue` 与 `enqueueWithActivity` / `enqueueWithBlock` 共用同一份去重实现。
- **优先级 `LOW`**：同一个区块里的截图先分析完，汇总才更有内容。实时截图仍然是 `NORMAL`，
  启动补偿也是 `LOW`。
- `AIWorker` 新增 `providers`（按 Job 类型覆盖 Provider）：汇总任务走文本 Provider，
  截图分析仍然走视觉 Provider。顺带：

  - 兜底超时按 Provider 的 `timeoutMs` 走（汇总 300s vs 截图 120s）；
  - 健康检查并发探测所有 Provider，模型可用性**按 Provider 分别记录**——汇总模型缺失时
    不该把截图分析一起判失败（反之亦然）；
  - `snapshot()` 里的 `modelAvailable` 仍然表示主 Provider（视觉模型）的可用性。

- 汇总任务不关联 `activities`，`ai_jobs.activity_id` 固定为 `NULL`。

## 8. 崩溃恢复

区块行与 Job 在同一个事务里写入，因此**两者要么都在、要么都不在**。据此：

| 被杀时的位置 | 重启后的行为 |
| --- | --- |
| 事务提交之前 | 区块与任务都不存在 → 缺口扫描重新排队 |
| 事务提交之后、汇总完成之前 | 任务停在 `PROCESSING` → `queue.start()` 恢复为 `PENDING` 继续跑；区块行已存在，扫描不会重复排队 |
| 汇总完成之后 | 区块 `COMPLETED`，任务 `COMPLETED`，扫描跳过 |

第二种情况正是「区块行存在性 = 处理过」这条不变式的价值所在。

## 11. 留给后续 Phase 的问题

- **汇总会带上还没分析完的记录**：如果时段内多数截图仍停在 `PENDING`，汇总质量会下降。
  当前只保证「有记录就汇总」，没有「等这一时段全部分析完再汇总」的等待条件。
- **失败区块不会自动重试**：`FAILED` 的区块行一直存在，缺口扫描不会再排队，需要手动重新汇总
  （本阶段没有这个入口）。
- **分类可能不是四个中文枚举**：Schema 约束了 `enum`，但模型偶尔会输出近义说法，此时按
  `INVALID_RESULT` 重试；用弱模型时可能连续失败。
- **描述偏短**：需求是「1000 字左右」，实测 `qwen3-vl:8b` 在关掉思考后稳定输出 280~440 字，
  高于 200 字的校验下限所以不会报错，但离目标还有距离。要拉长只能改提示词（例如明确要求
  分段与最小字数），代价是耗时上升。
- **软件名是自由文本**：不同区块可能写成「VS Code」/「Visual Studio Code」，筛选下拉会出现两行。
  没有做归一化或别名表。
- **上一时段上下文只取「最近一条 COMPLETED」**：中间的空档（没开机的时段）与失败区块会被跳过，
  所以「沿用上一个项目名」在长时间中断后可能不成立。
- **`summaryModel` 默认与视觉模型共用**：同一个模型既看图又写摘要，用文本模型专门做汇总可能更省显存。
- **区块扫描上限 144**：超过 24 小时的历史缺口一次扫不完，靠后续每 10 分钟一轮慢慢补，
  首次使用旧数据库时要等若干轮。
