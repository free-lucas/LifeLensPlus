# 看板与统计（Phase 9）

## 1. 目标与范围

需求：按**天 / 周 / 月 / 年**四个周期，把已经落库的数据尽可能多地用起来，做成一张能一眼看完的看板。

- 时间轴：周期切换 + 上一期 / 下一期 / 回到今天 / 跳到某一天；
- 图表：时间分配环形图、活动趋势（分类堆叠柱 + 截图记录折线）、时段分布、
  项目专注时长排行、软件使用次数排行、关键词云、待办线索、顶部五个统计卡片；
- 只读：看板不写任何数据，也不触发任何 AI 任务。

不做的事：不做自定义周期、不做数据导出、不做同比 / 环比、不做图表的缩放与平移、
不引入图表库（全部手写 SVG）。

## 2. 周期口径

`src/main/stats/period.js` 是唯一的周期口径，渲染层**不做任何日期数学**。

| 周期 | 边界 | 趋势分桶 |
| --- | --- | --- |
| `day` | 锚点当天 `[00:00, 次日 00:00)` | 24 个小时 |
| `week` | 锚点所在周（**周一起始**）`[周一, 下周一)` | 7 天 |
| `month` | 自然月 | 当月天数（28~31） |
| `year` | 自然年 | 12 个月 |

- **锚点**（`anchor`，`YYYY-MM-DD`）只用来记住用户看到哪一天，具体边界由周期决定：
  从「本周」切到「月」看的就是这一周所在的月份；
- 回参里带 `prevAnchor` / `nextAnchor`（上一期 / 下一期的起点日期），界面直接回传，自己不算日期；
- `hasToday`：今天是否落在这一期里（为真时「下一期」按钮禁用）；
- `future`：**整段都在未来**（还没开始）时为真，界面同样禁用「下一期」；
- 非法周期回退 `DEFAULT_PERIOD = 'week'`，非法 / 空锚点回退今天。

```js
resolvePeriod('week', '2026-09-16')  // -> from 09-14 / to 09-21 / label '2026年9月14日 – 20日'
                                     //    prevAnchor 09-07 / nextAnchor 09-21 / hasToday true
```

## 3. 聚合数据层

`StatsRepository.summarize({ period, anchor })` 一次查询返回这个周期的**全部**聚合结果。
SQL 只负责把行读出来，聚合规则（占比、时长、分桶、排行）在纯函数 `stats/summarize.js` 里，
两边职责不重叠。

| prepared statement | 读出来的行 |
| --- | --- |
| `totalsStatement` | 区块总数 / 已汇总 / 汇总中 / 失败 |
| `categoryStatement` | `GROUP BY category` 的区块数 |
| `projectStatement` | `GROUP BY project`（排除空值）按区块数倒序 |
| `softwareStatement` | `json_each(software_json)` 展开后按软件名分组 |
| `hourStatement` | `substr(block_start,12,2) × category` 的区块数 |
| `dailyStatement` | `substr(block_start,1,10) × category` 的区块数 |
| `dailyActivityStatement` | 每天一条：截图记录数 |
| `hourlyActivityStatement` | 每小时一条：截图记录数 |
| `keywordStatement` | `json_each(keywords_json)` 展开后按关键词分组 |
| `todoStatement` | `json_each(todos_json)` 展开，带 `MIN(substr(block_start,1,10))` 最早出现日 |
| `activityCountStatement` / `projectCountStatement` / `softwareCountStatement` | 三个计数 |

所有查询都是「一段时间内的若干行」，年视图最坏情况下也就 366 行 / 12 行 / 24 行，没有整表扫描。

## 4. 二次汇总（`buildStats`）

纯函数，不碰数据库、不碰 DOM，输入是一批小 SQL 结果，输出是界面可以直接画的完整结构：

```text
{ period, blockMinutes,
  totals:    { blocks, completed, pending, failed, minutes, activities, activeDays, days },
  categories:[{ category, blocks, minutes, share }],   // 固定四类，缺失补 0
  projects:  [{ label, blocks, minutes, share }],
  software:  [{ label, blocks, minutes, share }],
  hourly:    [{ hour, blocks, minutes, byCategory }],   // 固定 24 槽
  trend:     [{ key, label, startMs, future, blocks, minutes, activities, byCategory }],
  keywords:  [{ keyword, count }],
  todos:     [{ todo, day, count }],
  counts:    { projects, software } }
```

口径与约定：

- **时长 = 区块数 × 10 分钟**（`BLOCK_MINUTES`），只统计 `status = 'COMPLETED'` 且有 `category` 的区块；
- 分类固定是「娱乐 / 工作 / 学习 / 社交」四项（与 `SUMMARY_CATEGORIES` 同一份口径，
  `test/statsRepository.test.js` 有用例守着两者一致），数据里出现过的其它分类追加在后面；
- `share` 是占**已汇总时长**的比例，`totals.minutes` 就是所有分类分钟数之和；
- 排行按分钟数倒序、同名再按名字升序，条数上限 `DEFAULT_LIMITS = { projects: 12, software: 12, keywords: 20, todos: 20 }`；
- `activeDays` 把「有区块」与「有截图记录」都算成活跃天（一天里删过截图也算），`days` 是这一期的自然日数；
- 没有任何记录的周期也返回完整骨架（四个分类、24 个小时槽、空排行），界面因此不需要写一遍空态判断。

## 5. 图表

`src/renderer/kanban.js` 里所有几何计算都是纯函数，测试直接断言数值。

| 面板 | 纯函数 | 说明 |
| --- | --- | --- |
| 时间分配 | `donutSlices` / `renderDonut` | 132×132 的 SVG，半径 46、线宽 16（周长 289.03）；每类一段 `stroke-dasharray`，用负 `stroke-dashoffset` 前移，`rotate(-90)` 从 12 点开始；圆心写总时长；0 分钟的分类不画扇区，四类之外的取值用 `chart-bar-other` 兜底色 |
| 活动趋势 | `trendGeometry` / `renderTrendChart` | 720×220，柱宽 clamp 到 2~34；每柱按固定分类顺序从下往上堆叠（高度 = 分钟 / 最大值 × 绘图高）；折线画截图记录数（`activities`），超过 40 个点按间隔抽稀；三条刻度线（0 / 50% / 100%） |
| 时段分布 | `hourlyTrend` + `renderTrendChart` | 一天 24 小时的分布，高 180；**日视图的趋势本身就是时段分布，所以日视图不重复画这一块** |
| 项目专注时长 | `rankGeometry` / `renderRankChart` | 360 宽的横向条，行高 20、间距 8、标签列 128、数值列 74；条长按最大值归一化 |
| 软件使用次数 | 同上 + `valueText` | 数值列显示「N 次」而不是时长 |
| 关键词 | `renderKeywords` | 字号按出现次数分三档（`tag-lg` / `tag-md` / `tag-sm`） |
| 待办线索 | `renderTodos` | 待办 + 最早出现的那一天 |
| 顶部卡片 | `renderStatCards` | 已汇总时长 / 时间段（失败数作注脚）/ 截图记录 / 活跃天数 / 平均每天 |

面板数量：**周 / 月 / 年视图 7 块，日视图 6 块**（`test/kanbanView.test.js` 有用例守住）。

## 6. 渲染约定（CSP 约束）

页面 CSP 是 `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' file:`，
所以：

- **绝不写内联 `style="..."`**，宽度 / 高度 / 颜色 / 位置一律走 SVG 表现属性（`x` `y` `width`
  `height` `rx` `stroke-dasharray` …）与 CSS 类名（`.cat-fun` / `.cat-work` / `.cat-study` / `.cat-social`、
  `.rank-bar-0..3`）；
- 不用 `<canvas>`（渲染进程拿不到 Node，也不需要 canvas）；
- 所有会进 HTML 的文本（项目名、软件名、关键词、待办）都过 `escapeHtml()`；
- 空态是文案 + `class="timeline-state"`，不是空白。

## 7. 数据流

```text
renderer/kanban.js
  -> preload.getStats({ period, anchor })
  -> statsIpc: lifelens:stats
  -> StatsRepository.summarize
  -> stats/summarize.buildStats（纯函数二次汇总）
  -> renderKanbanReport -> #kanban-cards / #kanban-charts
```

一个周期只走一次 IPC：日期边界、占比、时长、分桶全在主进程算好，渲染层只负责画。

## 8. 本阶段发现并修复的问题

- **`resolvePeriod().future` 的语义写反了**：实现写的是 `to <= now`（**整段都在过去**），
  而注释、界面与需求要的都是「整段都在未来」。看板的「下一期」按钮因此完全反着来：
  已经过完的周期点不动「下一期」，未来的周期反而能一直往后翻。
  修复为 `from > now`，并补了 `test/statsRepository.test.js` 的两条边界用例（补测时发现）。
- **`software_json` 里的重复名字**：SQL 用 `json_each` 展开后 `COUNT(*)`，
  同一个区块里重复写两次的软件会被算两次。当前由上游 `summaryOutput.normalizeStringList`（去重）保证不会出现，
  SQL 层不做额外去重。
- 关键词 / 待办 / 软件这些 `json_each` 展开都带了 `json_valid(...)` 条件，
  一行脏数据不会让整次统计报错。

## 10. 留给后续 Phase 的问题

- 软件名仍是自由文本，同一软件的不同写法（`Chrome` / `Google Chrome`）在排行里各占一行；
- 时长为空的周期只能看到「0 分钟」，没有「最近一次有数据的周期」快捷入口；
- 年视图的截图记录折线在 12 个桶下分辨率较低，没有按月聚合的第二种口径；
- 看板不区分「今天还没过完」，日视图的 `activeDays/days` 对比会显得偏低。
