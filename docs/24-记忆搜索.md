# 记忆搜索（Phase 11）

## 1. 这一页是什么

「搜索」标签页：用一句自然语言，在自己的历史记忆里找到最接近的片段。

- 检索范围是三层记忆：20 秒 Activity、10 分钟 Block Summary、1 天 Diary；
- 一条链路：查询文本 → embedding → 三张向量表各查一次 → 按相关度合并排序 → 回 SQLite 取完整记录；
- 这一阶段只做**语义搜索**：不做问答、不做多轮、不做 RAG / Query Rewrite / Reranker / Hybrid Search；
- 检索逻辑全部在 Main 层，Renderer 只通过 IPC 拿结果（不接触 LanceDB，也不接触 SQLite）。

## 2. 分层结构

```text
Renderer（renderer/search.js）
  -> preload.js          window.lifelens.searchMemories(query, limit)
  -> searchIpc.js        lifelens:memory-search
  -> MemorySearchService 聚合三表 / 合并排序 / 回查 SQLite
       ├── EmbeddingProvider.embedText        查询文本 -> 查询向量
       ├── MemoryVectorRepository × 3         activity_vectors / block_vectors / diary_vectors
       └── 现有 SQLite Repository              ActivityRepository / TimeBlockRepository / DiaryRepository
```

职责边界（与 Phase 10 相同口径）：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| `renderer/search.js` | 输入、Loading / 空 / 错误态、结果卡片、最近搜索、跳转指令 | 不做向量计算、不访问 LanceDB / SQLite |
| `searchIpc.js` | 把服务暴露成一个 IPC 通道；服务未装配时给可读错误 | 不含检索规则、不写 SQL |
| `MemorySearchService` | 三表聚合、`_distance` 合并排序、来源类型解析、结果整形、异常语义 | 不 require LanceDB 原生模块、不写过滤 SQL、不做 Prompt |
| `MemoryVectorRepository` | 单张向量表的检索（Phase 10 已有） | 不认识业务字段 |
| `db/repositories` | 按业务键回查完整记录（`getById` / `getByStart` / `getByDay`） | 不含检索逻辑 |

## 3. 搜索数据流

```text
用户输入
  ↓
provider.embedText(text)                 ← 与写向量时同一个 Provider、同一份维度校验
  ↓
三张向量表各 search(vector, { limit })   ← 复用 MemoryVectorRepository.search，返回含 _distance 的原始行
  ↓
按 _distance 升序合并（同距离按「层顺序 + source_id」兜底，保证顺序稳定可断言）
  ↓
截取前 limit 条
  ↓
按来源类型回查 SQLite（activity → getById / block → getByStart / diary → getByDay）
  ↓
items[] 返回给渲染层（只返回命中条数，不加载全部历史）
```

返回结构：

```js
{
  query, limit,
  items: [ { key, sourceType, sourceLabel, sourceId, distance,
             time, day, endTime, timelineId,
             title, content, project, category, keywords, keywordsLabel } ],
  hits, returned,
  layerCounts: { activity, block, diary },
  missing, invalid, elapsedMs, model,
}
```

各层在结果卡片上展示的字段：

| 来源 | 时间 | 正文 | 项目 / 分类 | 标签行 |
| --- | --- | --- | --- | --- |
| `activity`（20秒记录） | `captured_at`，到分钟 | `analysis.summary`（标题取 `analysis.activity`） | 有 | 关键词 |
| `block`（10分钟汇总） | 区块起止 `start–end` | `description` | 有 | 软件 |
| `diary`（日记） | `day`，只到天 | `summary` | 无 | 主要事项 |

## 4. 来源类型与 source_id 解析

向量表里**没有 `source_type` 列**（Phase 10 的约定）：来源类型由「查的是哪张表」决定，
行 ID 前缀（`activity:` / `block:` / `diary:`）与表一一对应。

```js
SOURCE_LAYERS = {
  activity: { table: 'activity_vectors', idPrefix: 'activity', label: '20秒记录' },
  block:    { table: 'block_vectors',    idPrefix: 'block',    label: '10分钟汇总' },
  diary:    { table: 'diary_vectors',    idPrefix: 'diary',    label: '日记' },
}
```

`source_id` 的取值顺序：

1. 优先取向量行里的 `source_id` 列；
2. 列缺失（老数据 / 手工写入）时，退回到按行 ID 前缀解析（`activity:123` → `123`）；
3. 两步都拿不到 → 这一条记为 `invalid` 跳过，不影响整次搜索。

回到 SQLite 时，同一个 `source_id` 在三层的语义不同：

| 来源 | `source_id` | 回查方法 |
| --- | --- | --- |
| `activity` | `activities.id` | `ActivityRepository.getById` |
| `block` | `block_start`（`time_blocks` 的业务键） | `TimeBlockRepository.getByStart` |
| `diary` | `day`（`diaries` 的业务键） | `DiaryRepository.getByDay` |

## 5. 结果跳转：复用已有页面

搜索页不新建详情页，点结果只做「切标签页 + 定位」：

| 来源 | 跳转 |
| --- | --- |
| `activity` / `block` | 切到「记录」，`timeline.focus(range, id)` 进入定位模式 |
| `diary` | 切到「日记」，`diary.selectDay(day)` 选中那一天 |

跳转指令由纯函数 `jumpTargetOf(item)` 算出（可单测），`applyJump(target, views)` 负责执行；
标签页切换复用 `renderer.js` 暴露的 `window.lifelensTabs.select`，不复制一份 class 切换逻辑。

时间线定位模式（`timeline.js` 新增）：

- `focus(range, id)` 用给定窗口查询，而不是当前筛选条件；渲染时在最前面加一条
  「已定位到搜索结果的记录」横幅与「查看完整时间线」按钮；
- 命中的那张卡片加 `.timeline-card-focus` 高亮（只改边框与内阴影，不改尺寸，避免滚动位置跳动）；
- 定位模式下**不把新记录插进列表**：列表是某个历史窗口的切片，插入会破坏「看到的就是搜索结果那一段」；
- 退出方式：点「查看完整时间线」调用 `clearFocus()`，或改动筛选条件（改筛选会退出定位并回到筛选查询）。

定位窗口的粒度：

- `block` 用 `[start, end)`，即那 10 分钟；
- `activity` 用 `[captured_at, captured_at + 1s)`，因为它只记录一个瞬间；
- 两边都是闭开区间，与 Timeline 的时间口径一致。

## 6. 最近搜索

- 存在 `localStorage` 的 `lifelens.search.recent`（界面状态，不是记忆数据）；
- 去重、最新的在前、上限 8 条；
- 读出坏数据（非 JSON / 非数组）时当作没有历史，不能因此让搜索页起不来；
  写入失败（隐私模式 / 配额）只影响这一块，搜索本身照常。

## 7. 异常语义

| 情况 | 表现 |
| --- | --- |
| 查询为空 | 直接返回空结果，不调用 Ollama；界面提示「先输入一句话，再开始搜索。」 |
| Embedding 未装配 | `INDEX_UNAVAILABLE`：记忆搜索不可用：Embedding 未装配 |
| 嵌入失败（Ollama 没跑 / 模型缺失 / 超时） | `EMBEDDING_UNAVAILABLE`，界面显示剥掉 Electron 前缀的原因 |
| 三张表一层都没装配 | `INDEX_UNAVAILABLE`：向量索引没有装配任何一层 |
| 三张表全部检索失败（原生模块缺失 / 库被删 / 维度不匹配） | `VECTOR_UNAVAILABLE` |
| 只有一 / 两层失败 | 其余层照常返回，失败层记 `MEMORY_SEARCH_ERROR` 日志 |
| Embedding 返回非数值向量 | `INVALID_RESULT` |
| 向量库没有数据 | 正常返回空 `items`，界面显式给「没有找到相关的记忆」 |
| `source_id` 对应的 SQLite 记录不存在（记录已删、向量还在） | 记为 `missing` 跳过这一条 |
| 行 ID 前缀对不上 / `source_id` 取不出来 | 记为 `invalid` 跳过这一条 |
| 单条 SQLite 读取抛异常 | 记为 `invalid` 跳过这一条，其余结果照常返回 |

**任何单条异常都不会让整页搜索失败**：单层失败降级为「少一层候选」，单条失败降级为「少一条结果」。

日志只记元信息（命中数、各层候选数、耗时、缺失 / 跳过条数），**不记查询文本**——
与「日志不含截图内容 / Prompt」的口径一致。

## 8. 性能与边界

- 默认 `limit = 20`，上限 `50`；非法值或非正数回落到默认值；
- 每张向量表最多查 `limit` 条，合并后只截取前 `limit` 条；
- Renderer 每次只拿到最终结果，不做「先拉全量再前端过滤」；
- 查询向量没有缓存：同一个词再搜一次会重新嵌入（语义搜索要求写读同模型，缓存留给后续阶段）；
- 检索只有向量一层，没有关键词 / 时间过滤，也没有 Reranker。

## 10. 已知限制

- **删除记录不会同步删向量**：向量还在，回查 SQLite 找不到时只算 `missing`，
  界面上表现为「各层候选数比结果数多」；
- **日记结果的 `project` / `category` 为空**：`diaries` 表本身没有这两个字段（Phase 9 的 Schema 决定），
  日记卡片只有「主要事项」标签行；
- **候选名额被密集层占用**：每层各查 `limit` 条再合并截取前 `limit` 条，
  某一层特别密集时（例如 20 秒记录）它的候选会占掉大部分名额；
- **同一句话每次都要重新嵌入**：没有查询向量缓存，首次搜索多花一次 Ollama 往返
  （冒烟实测 29～34ms，不含冷启动的模型加载）；
- **没有结果分页**：一次只给 `limit` 条，没有「加载更多」。
